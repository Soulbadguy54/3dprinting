# RateApp — повторный аудит после Stability & Performance (16.10.2026)

## Подтверждённое состояние

- Production: https://rateapp-delta.vercel.app
- Стек: React/Vite PWA, FastAPI, PostgreSQL/Neon, IGDB, Web Push, Vercel.
- /api/health: HTTP 200, PostgreSQL reachable, IGDB configured.
- Отчёт /api/health о целостности: `unresolvedTargetRows=0`,
  `constraintValidated=true`. Числа исторической миграции относятся
  к 15 октября, а не к текущему релизу.
- GitHub Actions: TypeScript + Vite build + ограничение размера стартового JS;
  backend unittest с реальной PostgreSQL и Alembic;
  Playwright мобильный Android Chromium + iPhone WebKit;
  production smoke для API/авторизации.
- До оптимизации стартовый JS весил около 1147 КБ (gzip около 300 КБ);
  после отложенной загрузки эмоджи основной чанк ~492 КБ
  (gzip ~154 КБ). Это измерение размера сборки, не Core Web Vitals.

## Реализовано и проверяется CI

1. **Миграции:** Alembic вне serverless cold start. Первая миграция
   ничего не меняет в уже существующей БД: проверяет необходимые таблицы
   и колонки, затем регистрирует baseline. При частичной схеме —
   явный отказ. Регрессионные тесты на чтение существующей схемы.
2. **Восстановление сессии:** только HTTP 401 означает неавторизованного
   пользователя. HTTP 5xx, сбои сети и ошибки разбора ответа ведут на
   экран повтора, а не на форму входа.
3. **Backend:** SQL eager-loading данных игр, атомарное обновление
   только изменённых связей игр и коллекций; сохранение оригинальных
   дат связей. API разделён по модулям авторизации, коллекций,
   библиотеки, игр/IGDB и Web Push.
4. **Frontend:** выделены компоненты карточек игр, иконок, колеса
   оценок, оформления коллекций и профиля. Индексы ID игр и
   связей коллекций вместо повторяющихся линейных поисков.
5. **Размер PWA:** тяжёлый выбор эмоджи загружается по запросу.
   Версия отображается в профиле, обновление PWA требует явного
   подтверждения, чтобы не прерывать редактирование.
6. **Данные и вход:** экспорт только собственных прохождений,
   оценок, отзывов и коллекций в JSON. Новая регистрация требует
   PIN из 6–8 цифр; вход со старым 4-значным PIN сохраняется.
7. **Тестирование:** Playwright проверяет регистрацию, создание
   коллекции, экспорт и долгое нажатие с массовым удалением; проверяет
   ошибку загрузки без ложного разлогина. Backend тесты проверяют
   изоляцию пользователей, статусные переходы, рейтинги, миграции,
   Web Push и защиту от неверных данных.
8. **Доставка и наблюдаемость:** `npm ci` с lock-файлом,
   бюджет стартового JS в CI, smoke-проверки production после CI
   и ежедневная отдельная проверка работоспособности.
   Опциональный Sentry установлен на фронте и бэкенде с
   отключённым сбором тела запросов и персональных данных по умолчанию.

## Риски и ограничения, требующие следующих действий

**Операционная настройка (нельзя считать включённой только по коду):**

- **Мониторинг ошибок:** DSN для Sentry не настроен в окружении Vercel.
  Нужно зарегистрировать проекты и задать `SENTRY_DSN` и
  `VITE_SENTRY_DSN`; после этого проверить алерты и отсутствие PII.
  Ежедневный публичный smoke уже настроен через GitHub Actions, но он
  не заменяет полноценную трассировку ошибок.
- **Резервные копии и восстановление:** экспорт JSON не заменяет
  снимки PostgreSQL. Статус snapshot/PITR у Neon не подтверждён.
  Включить и проверить восстановление в отдельную БД через консоль Neon.
- **Release gate:** Vercel Git integration деплоит main до завершения
  тестов. Нужно включить GitHub branch protection + Vercel Deployment
  Checks / protected promotion; текущая GitHub-интеграция не имеет
  доступа к настройкам branch protection (HTTP 403).
- **Production Alembic revision:** код миграций и проверки подготовлен,
  CI использует их на тестовой БД, но версия миграций на реальном Neon
  **не проставлена в рамках этого изменения**. Проставить baseline в
  защищённом процессе с backup/restore test и полномочиями на БД;
  не запускать неоговорённые автоматические DDL на production.

**Технический долг:**

- `src/App.tsx` всё ещё около 3250 строк, хотя наиболее повторно
  используемые компоненты и профиль уже выделены. Следующий этап —
  разделение крупных экранов и состояний по отдельным хукам/модулям
  с сохранением поведения и навигации.
- `src/styles.css` около 3860 строк; стили коллекций и колеса
  оценок уже выделены. Имеет смысл постепенно делить остальные
  стили по экранным компонентам.
- Ещё нет измерений Core Web Vitals на реальных устройствах и
  стресс-тестирования IGDB/Neon при большом количестве пользователей.
- Профиль показывает недоступность изменения email/PIN; это
  отдельная функциональность с обязательной повторной проверкой PIN.

## Рекомендованный операционный порядок

1. Включить бэкапы/PITR и выполнить проверку восстановления.
2. Подключить Sentry с фильтрами PII и алертами.
3. Включить GitHub branch protection и Vercel Deployment Checks.
4. В защищённой среде проверить и зарегистрировать Alembic baseline
   на production, не переписывая исторические строки.
5. Продолжить дробление крупных экранов только с зелёным мобильным
   CI и production smoke после каждого изменения.

Не считать все эксплуатационные зависимости закрытыми до реальной
настройки и независимой проверки соответствующих сервисов.
